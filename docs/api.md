# API

Versioned REST API under `/api/v1`. The OpenAPI document is at `/openapi/v1.json` and Swagger UI at `/swagger`. They
are the source of truth for routes, schemas, status codes and the `Idempotency-Key` header. Their descriptions come
from the XML comments in `OrderProcessing.Api`, so change behaviour there and they follow.

Endpoints: `POST /orders`, `POST /orders/{orderNumber}/resubmit`, `GET /orders?userId=`, `GET /payment-gateways` and
`GET /currencies`.

The API has no authentication. The `userId` is supplied by the caller and is not verified (see
[Scope and non-goals](architecture.md#scope-and-non-goals)).

## Idempotency key

`POST /orders` needs an `Idempotency-Key` header, generated by the client once per order attempt and reused only to
retry that same request. It is not the order number, which the server generates. A repeat with the same key and payload
never creates another order or charge, and the same key with a different payload returns `409`. Keys are scoped to the
`userId`. The full contract is in the remarks of `OrdersController.Submit`; how it is enforced is in
[architecture](architecture.md#idempotency-and-concurrency).

## Error bodies

- `422`: the gateway declined. The body has `orderNumber` and a `message` that is safe to show to the end user. The order
  is `Failed` and can be resubmitted.
- `504`: the gateway did not answer within `Payments:GatewayTimeout` (default 30 seconds). The payment may or may not
  have gone through, so the order stays `Pending` (not `Failed`). The problem body contains `orderNumber`. Retry with
  the same `Idempotency-Key`, or resubmit the order. A real gateway must deduplicate on the order number, because the
  retry charges again.
